pov39-render-worker 1.3.0 — release manifest (branch feat/timeline-v2-renderer, NOT DEPLOYED)

CHANGES SINCE 1.2.0
  - Timeline V2 (schema_version 2) renders through src/render/v2/compose.py: lower thirds, pills,
    credits, headlines, quotes, stamps, image cards, speaker zoom on the footage, fade/dissolve/slide,
    music bed under the original speech, ASS subtitles at output resolution. V1 is unchanged.
  - V2 timelines are refused with named reasons and a full problem list (see BASE44-PATCH.md).
  - inputs.sources accepts the Base44 mediaPipeline array shape (previously every such request was a 400).
  - New operations: frame_extract, scene_detect, audio_analyse, transcribe (transcribe only on an image
    built with WITH_ASR=1; it runs alone). New endpoint: POST /timelines/validate.
  - Per-job timeouts, Idempotency-Key conflict detection (409), image uploads, preview stills of V2 renders.
  - Dockerfile adds python3, python3-pil, python3-numpy, libraqm0 (~60 MB). Optional ASR layer ~600 MB.
  - DB migration (automatic, additive): render_jobs.result jsonb, render_jobs.request_hash text.

KNOWN ISSUE, NOT CHANGED: V1 burned subtitles are ~3.3x too large (SRT through libass is laid out on a
  288-line canvas, the style sets pixel sizes). V2 does not have this. Fixing V1 changes V1 output, so it
  waits for approval.

pov39-render-worker 1.2.0 — release manifest

DEPLOY
  Build this archive (or push the worker/ folder to the Render repository) and redeploy the
  pov39-render-worker service. No environment variable is required for the new limits; the two new
  ones — REMOTION_CONCURRENCY and MOTION_MIN_MEMORY_MB — are optional and default to safe values.
  The health check path must stay /health (the light probe), never /health/deep.

CHANGES SINCE 1.1.0
  - Motion rendering no longer lets Remotion choose its own frame concurrency. Remotion reads the
    core count, which says nothing about memory; it is now pinned to half the cores, at most two
    browser tabs, overridable with REMOTION_CONCURRENCY.
  - A motion job is refused up front — quoting the container's measured memory — when the instance
    cannot hold a browser, instead of being crashed into repeatedly by the host.
  - The renderer's whole process group is torn down on timeout, abort and cancel, so an abandoned
    Chromium can no longer outlive its script and hold the memory the next attempt needs.
  - Leftover work directories and Remotion bundle directories are removed on boot: a worker killed
    mid-render never reached its own cleanup, and on a small instance those are the megabytes that
    decide whether the next attempt fits.
  - A job the host stops twice is failed with a plain explanation rather than retried a third time;
    the retry after an interruption is bounded to one.
  - Progress is written before the terminal row and can no longer be overwritten by a progress tick
    that was still in flight: a finished render reports 1.0, not a partial figure.
  - Every attempt records how the renderer's process ended (exit code, signal, kill reason, peak RSS
    of the whole render process group, host memory) on the job row, and prints the render's memory
    to the log every 30 seconds.
  - /health/deep additionally reports resources (measured container memory limit, use and peak, CPU
    count, worker RSS), motion_concurrency and active_jobs.
  - SIGTERM and unhandled errors are logged in their own words, so a platform stop can be told
    apart from a crash.
  - Simultaneous render jobs are capped at two.

UNCHANGED
  - The FFmpeg master/preview pipeline, the storage routes, the job contract and the validation
    rules. FFmpeg output is byte-for-byte the same pipeline as 1.1.0.

KNOWN PRODUCTION CONSTRAINT
  - Memory. A motion render is limited by the browser, not by the CPU, and the service runs on
    Render's "standard" instance (2 GB, 1 vCPU) as configured in render.yaml. If a render is
    interrupted twice, the job now fails with that explanation and the credits are returned by the
    app; the instance type is the next thing to change.
